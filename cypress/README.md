# Cypress E2E Testing for Decibel Tribe

This directory contains all End-to-End (E2E) tests for the Decibel Tribe application, implemented using [Cypress](https://www.cypress.io/).

The goal of these tests is to simulate real user workflows and verify the application's functionality from the user's perspective after different parts (frontend, backend, database) are integrated.

## Project Structure

The Cypress tests and supporting files are organized as follows:

```
cypress/
├── e2e/                    # Contains the actual test spec files (.cy.ts)
│   ├── ui/                 # Tests primarily interacting with the User Interface
│   ├── api/                # Tests interacting directly with APIs (less common for E2E)
│   └── accessibility/      # Accessibility checks
├── factories/              # Test data generation functions (e.g., eventData.ts)
├── fixtures/               # Static test data, primarily text/messages (.json)
├── pages/                  # Page Object Model files (.ts)
├── screenshots/            # Automatic screenshots on failure (gitignored)
├── support/                # Reusable commands and configuration
│   ├── apiCommands.ts      # Custom commands for API interactions (e.g., cy.loginByApi)
│   ├── commands.ts         # Custom commands for UI interactions
│   ├── e2e.ts              # Main support file, imports commands
│   └── cypress.d.ts        # TypeScript definitions for custom commands
├── results/                # Test results (e.g., Mochawesome reports) (gitignored)
└── README.md               # This file
└── (Potentially other config/guide files like CYPRESS_TEST_WRITING_GUIDE.md)
```

## Running Tests

Ensure you have installed all project dependencies in the root of the project, not in the cypress directory (`npm install`). You may also need to seed your database (`npm run db:seed`) before running tests that rely on specific data, please check your database.

Key commands (run from the project root):

- **`npm run cy:open`**: Opens the interactive Cypress Test Runner GUI. Best for writing and debugging tests locally.
- **`npm run cy:run`**: Runs the tests in the headless browser. Best for CI/CD pipelines.
- **`npm run cy:nightly:report`**: Runs the _full_ E2E suite headlessly (no GUI). This is typically used in CI environments or for scheduled runs. It also generates reports.
- **`npm run cy:smoke:headless`**: Runs only the tests tagged as "smoke" headlessly. Useful for quick checks in CI.
- **`npm run cy:smoke`**: Opens the Cypress GUI filtered to show only "smoke" tests.

## Key Concepts & Conventions

- **Page Object Model (POM):** We use Page Objects (in `cypress/pages/`) to encapsulate element selectors and interaction logic for specific pages or components, improving maintainability.
- **Custom Commands:** Reusable sequences of actions are defined in `cypress/support/commands.ts` (for UI interactions) and `cypress/support/apiCommands.ts` (for API interactions, often used for setup like logging in).
- **Selectors:** We prioritize selectors that closely mimic how a user finds elements and are resilient to styling changes. Please follow this order of preference when selecting elements:
  1.  **Content & Role/Type:** Select elements based on their visible text content combined with their role or element type (e.g., `cy.contains('button', 'Save')`, `cy.get('button').contains('Save')`). This aligns best with user interaction and manual test documentation.
  2.  **Developer-Defined Attributes:** Use stable, intentionally added attributes like `id`, a meaningful `class` (not one automatically generated by a styling framework like Bootstrap/Tailwind utility classes), or `aria-label` that have been deliberately named by the development team.
  3.  **`data-testid` Attribute:** If the above methods aren't suitable or stable enough (e.g., for dynamic text or complex components where text/role isn't unique or IDs aren't practical), request or add a specific `data-testid="your-unique-identifier"` attribute to the element in the application code as a dedicated testing hook.
  4.  **Avoid:** Relying heavily on complex CSS selectors based purely on DOM structure (e.g., `div > span + div nth-child(3)`) or selectors tied directly to framework-specific styling classes like `cy.get('.h3729Dr142')`, as these are often brittle and likely to break with minor UI updates, or version updates.
- **Test Data:**
  - Use `cypress/fixtures/` for static data (e.g., validation messages).
  - Use `cypress/factories/` for generating dynamic, realistic test data (e.g., user details, event data).
- **Waiting:** Avoid fixed waits (`cy.wait(number)`). Use Cypress's built-in retry-ability, wait for network requests using `cy.intercept()`, or assert on UI changes.

(For more detailed conventions, refer to the `CYPRESS_TEST_WRITING_GUIDE.md` if available.)

## Contributing to Cypress Tests

Contributions to the E2E test suite are welcome, especially for critical user flows and new features.
(Optional/Recommended) - Use cursor/rule `cye2e.mdc` for Cypress Expert Prompt and `cypress/CYPRESS_DEBUGGING_WORKFLOW.md` to trigger a Cypress debuging workflow for Cypress tests.

1.  **General Process:** Follow the main project contribution guidelines outlined in `../../CONTRIBUTING.md` regarding branching, commit messages, and the Pull Request process.
2.  **Placing Tests:** Add new test files (`.cy.ts`) to the appropriate subdirectory within `cypress/e2e/` (e.g., `ui/authentication/`, `accessibility/profile/`).
3.  **Use Existing Abstractions:** Before adding new selectors or complex actions, check `cypress/pages/` for relevant Page Objects and `cypress/support/` for existing commands. Leverage these to keep tests DRY (Don't Repeat Yourself).
4.  **Data Management:** Use factories (`cypress/factories/`) for dynamic data and fixtures (`cypress/fixtures/`) for static data as appropriate.
5.  **Checks:** Before submitting a Pull Request that includes changes to the `cypress` directory, ensure your code passes the relevant checks by running:
    - **`npm run cy:check:all`**: This command runs ESLint (`cy:lint`) and TypeScript checks (`cy:types`) specifically for the Cypress codebase.

## Debugging

- Use the **Cypress Test Runner GUI** (`npm run cy:open`) for interactive debugging, stepping through commands, and inspecting the DOM/network.
- Use `cy.log('message')` to print information to the Cypress command log.
- Use `debugger` statements in your test code and open browser dev tools.
- Check the automatically generated screenshots and videos (if enabled) in `cypress/screenshots/` and `cypress/videos/` on test failure during headless runs.

## End-to-End Tests (Cypress)

- Used for testing complete user flows through the application UI. Primarily managed by the QA team, but developers might run them occasionally.
- Find tests in the `cypress/e2e/` directory.
- **Running Tests:**
  - `npm run cy:open`: Opens the interactive Cypress Test Runner GUI (best for local debugging/writing).
  - `npm run cy:nightly:report`: Runs the full E2E suite headlessly and generates reports (used mainly in CI/scheduled runs).
  - `npm run cy:smoke`: Opens the Cypress GUI filtered to run only "smoke" tests.
  - `npm run cy:smoke:headless`: Runs only "smoke" tests headlessly.
- **Static Checks for Cypress Code:**
  - **`npm run cy:check:all`**: Runs both `cy:lint` and `cy:types`.
    - `npm run cy:lint`: Runs ESLint specifically on the `cypress` directory.
    - `npm run cy:types`: Checks TypeScript types within the `cypress` directory.
- **Note:** E2E tests often require a specific database state. Utilize the seeding script (`npm run db:seed`) or custom Cypress commands (`cypress/support/`) for setup/teardown, check your database.
